Deployment Runbook

Getting CIPRMS onto Render with Atlas

Five things stood between this app and a working Render deploy. Four are already fixed in the code — the rest is Atlas and dashboard configuration you have to do by hand.

MongoDB Compass→ Atlas cluster→ GitHub→ Render web service
Diagnosis

Why it wasn't connecting

The port was hardcoded to 3000

Fixed in code

Render assigns a port and injects it as PORT. Binding to 3000 anyway means Render never sees an open port and kills the deploy with “Port scan timeout reached, no open ports detected.” Now reads process.env.PORT.

The database name was missing from the connection

Fixed in code

This is the subtle one. The string Atlas gives you ends at .mongodb.net/?retryWrites=… — no database in the path. client.db() with no argument then silently falls back to a database called test, so the app connects perfectly and every page reads back empty. The database is now named explicitly via MONGO_DB_NAME, for both the app and the session store.

Sessions couldn't survive Render's proxy

Fixed in code

Render terminates HTTPS at its edge and forwards plain HTTP inward. Without app.set('trust proxy', 1), Express thinks the request is insecure, refuses to send the secure session cookie, and every login bounces straight back to the sign-in page.

The server tried to open a web browser

Fixed in code

Startup called open(url) — useful locally, meaningless on a headless container. Now gated behind NODE_ENV !== 'production'.

Atlas is almost certainly blocking Render's IP

You must do this

Atlas rejects every connection from an address that isn't in Network Access. Render's free and starter tiers have no fixed outbound IP, so there is no single address to allow — and the failure looks like a 30-second hang ending in MongoServerSelectionError, not a permission error. Step 02 below.

Runbook · in order

What to do now

Create the Atlas database user

In Atlas: Database Access → Add New Database User. Password authentication, built-in role Read and write to any database.

Then generate the password with Atlas's Autogenerate Secure Password and copy it immediately. If you type your own and it contains @ : / ? # % &, you must percent-encode those characters inside the URI or authentication fails with a confusing bad auth:

# @ → %40   : → %3A   / → %2F   ? → %3F   # → %23   % → %25
# p@ss:word becomes
mongodb+srv://ciprms:p%40ss%3Aword@cluster0.xxxxx.mongodb.net/

Open Atlas Network Access to Render

Network Access → Add IP Address → Allow Access From Anywhere, which enters 0.0.0.0/0.

This is required because Render doesn't give you a stable outbound IP to allowlist on the free and starter plans. Your cluster stays protected by the database user's credentials, which is the only thing standing between it and the internet — so treat that password accordingly and never commit it.

If you're on a paid Render plan

Render's Standard plan and above expose static outbound IPs under Service → Connect → Outbound. Allowlist those three addresses instead of 0.0.0.0/0 and delete the open rule.

Move the Compass data into Atlas

Your local ciprms database has 18 collections. Atlas starts empty — nothing copies itself across, so the app will look broken until you migrate.

The fast way, if you have the MongoDB Database Tools installed (they ship separately from Compass):

mongodump --uri="mongodb://127.0.0.1:27017/ciprms" --out=./dump

mongorestore --uri="mongodb+srv://USER:PASS@cluster0.xxxxx.mongodb.net/" \
  --nsFrom="ciprms.*" --nsTo="ciprms.*" ./dump

The no-install way, straight from Compass — this is the same shape as the files already sitting in Database_backup/:

  • Connect Compass to 127.0.0.1:27017, open each collection, Export Collection → JSON.
  • Open a second Compass connection using the Atlas string, create the ciprms database, and Import JSON into a matching collection for each file.

Whichever route you take, the database on Atlas must be named exactly what you set as MONGO_DB_NAME in the next step. A capital letter or a stray plural is enough to give you an empty app.

Push to GitHub — without the secrets

.env is gitignored and is not tracked, which is correct: your Google client secret and session key stay off GitHub. That also means Render will never see them unless you enter them in the dashboard, which is step 05.

git add -A
git commit -m "Configure for Render deployment"
git push origin main

A new .env.example is included in this commit, documenting every variable without any real values.

Create the Render service and set its environment

New → Web Service, connect the GitHub repo, then:

  • Runtime Node · Build command npm install · Start command npm start
  • Leave the port field alone — Render injects PORT and the app now reads it.

Under Environment, add these. Every one of them is read by the server at boot:

KeyValue
MONGO_URIThe full mongodb+srv://… string from Atlas → Connect → Drivers, with the real password substituted in
MONGO_DB_NAMEciprms — must match the database you restored into
NODE_ENVproduction
SESSION_SECRETCopy from your local .env, or generate a fresh 32-byte hex value
GOOGLE_CLIENT_IDCopy from your local .env
GOOGLE_CLIENT_SECRETCopy from your local .env
GOOGLE_TOKEN_ENCRYPTION_KEYCopy from your local .env — changing this makes stored calendar tokens undecryptable

CALLBACK_URL from your local file is not needed — the app derives the OAuth callback from the incoming request host, so it adapts to the Render domain on its own.

Authorize the Render domain in Google Cloud

Once Render gives you a URL, go to Google Cloud Console → APIs & Services → Credentials, open the OAuth client, and add to Authorized redirect URIs:

https://your-service.onrender.com/auth/google/callback

Skip this and Google refuses the sign-in with Error 400: redirect_uri_mismatch. Keep the existing ngrok and localhost entries if you still develop against them.

Deploy and read the logs

A healthy boot prints exactly this, in this order:

✓ Connected to MongoDB successfully (database: ciprms)
✓ MongoDB connected — starting server...
CIPRMS server running → port 10000

The database name in that first line is your migration check. If it says test, MONGO_DB_NAME didn't get set and you'll be looking at an empty app.

When it fails, match the error

What you seeWhat it actually meansFix
MongoServerSelectionError — hangs ~30s, then “connection closed” Atlas is dropping the connection before it starts. Nearly always Network Access. Add 0.0.0.0/0 in Atlas Network Access. Confirm the rule shows Active, not Pending.
MongoServerError: bad auth : authentication failed Username or password is wrong, or a special character in the password broke the URI. Percent-encode the password, or reset it to an autogenerated one. Check the user exists under Database Access.
querySrv ENOTFOUND _mongodb._tcp.cluster0… The cluster hostname is mistyped, or mongodb+srv DNS lookups are blocked. Re-copy the string from Atlas → Connect → Drivers rather than editing the old one by hand.
App loads, every table and list is empty Connected to the wrong database — the old test fallback, or a name mismatch. Set MONGO_DB_NAME to the exact database name in Atlas. Verify against the boot log line.
Port scan timeout reached, no open ports detected Nothing bound to Render's assigned port. Already fixed — confirm the deploy is running the latest commit, not a cached earlier one.
Login succeeds but immediately returns to the sign-in page The session cookie is marked secure and never leaves the proxy. Already fixed by trust proxy. If it persists, confirm NODE_ENV and SESSION_SECRET are both set on Render.
Error 400: redirect_uri_mismatch Google doesn't recognize the Render callback URL. Add the onrender.com callback URI in Google Cloud Console credentials. Changes take a minute to propagate.
SSL alert internal error / TLS handshake failure Node too old for Atlas's TLS requirements. engines.node is pinned to >=20. Set NODE_VERSION=20 on Render if it still picks something older.
Before you rely on it

One thing Atlas doesn't solve

Moving the database to Atlas makes your records durable. Uploaded files are a separate problem. This app writes avatars, archived documents, and OCR temp files to uploads/ on the local disk — and Render's filesystem is ephemeral. Every deploy, restart, and idle-spindown wipes it.

Records will survive; the PDFs and profile pictures attached to them will vanish and leave broken links. The two ways out are a Render Persistent Disk mounted at uploads/ (paid plans only), or moving uploads to object storage such as S3, Cloudflare R2, or Google Cloud Storage. Neither is required to get the deploy green — but plan for it before the system carries real data.
